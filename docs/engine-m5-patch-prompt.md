Source findings:

1. `TalusCharacterController` in `src/simulation/RapierBridge.ts` initializes the configured offset through `configureCharacter({offset})`. `CharacterMovementSystem.applyConfig` later supplies slope/step/up/snap settings but omits offset. `src/simulation/rapier/TalusCorePhysics.ts:configureCharacter` fills omitted offset with **0.01**, so the configured 0.5 skin is lost. The test's floor clearance matches approximately 0.01. Preserve the complete effective configuration through the native boundary; do not silently reset omitted settings.
2. The movement system shares one CCT and applies settings at registration/update/deferred registration, rather than for every actor's solve. Verify distinct actors actually receive their own slope, step, snap and skin settings, independent of registration order. Use a complete cached configuration or per-controller state as appropriate; avoid unnecessary per-frame allocation.
3. Instrument the actual Rapier auto-step solve to identify why each small obstacle is rejected. The offset reset is a confirmed configuration defect, but has not yet been proven to be the sole cause of the step failures. The live body census shows the root is kinematic and has a Rapier body; the held weapon is cosmetic and has no Rapier body. Do not assume an untested self-collision explanation.
4. Powder support currently has fixed step/slope thresholds derived from `halfY` in `CharacterMovementSystem`. Check how that path and solid-terrain auto-step should honor the authored controller contract. Keep any needed extension general; no Indigo-specific branches.
